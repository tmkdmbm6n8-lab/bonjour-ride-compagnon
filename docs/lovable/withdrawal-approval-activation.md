# Activation Lovable : demandes de retrait avec validation admin

État : interface et appels serveur préparés ; NON activé en production. Ne pas annoncer une activation sans contrôler les RPC, Stripe, notifications et tâche planifiée. Le formulaire refuse tout envoi si la version de protocole manque. Aucun fichier de migration n’a été modifié ici (AGENTS.md).

## Consigne à donner à Lovable

Ajouter un circuit de demandes de retrait avant débit, compatible avec le code préparé dans `withdrawals.server.js`, sans modifier les calculs de courses, le lien de prix, les commissions, les frais de retrait existants (0,50 €), ni les montants déjà comptabilisés. La saisie et le bouton Tout le solde représentent le **total débité**. Minimum 10 € de débit, frais inclus : demande de 10 € -> net 9,50 €, frais 0,50 €. Une demande de tout le solde laisse zéro après validation, jamais un solde négatif.

1. Table privée `withdrawal_requests` : id UUID, driver_id, amount (net), fee, debit (amount+fee), status pending/processing/paid/rejected/failed, created_at, reviewed_by, reviewed_at, payout_id unique, notification_push_sent, notification_email_sent. Contraintes DECIMAL deux décimales, montant total >=10 €, montant net positif, une seule demande pending/processing par chauffeur. RLS : aucune mutation authentifiée directe, lecture propriétaire/admin au besoin ; fonctions uniquement service_role, révoquer PUBLIC/anon/authenticated. Valeurs et identité viennent exclusivement du serveur authentifié.
2. RPC `withdrawal_request_state(_driver uuid)` -> JSON `{version:1,requests:[...]}`. Si _driver fourni : demandes du chauffeur seulement. Si null : liste admin, avec driver_name, status, debit, amount, fee, created_at, payout_id et états de notifications. Trier récentes d’abord. Liste paginée ou limitée (ex. 100) avec demandes actives prioritaires. NE PAS retourner version 1 avant toutes les étapes terminées.
3. RPC `request_withdrawal(_driver uuid,_debit numeric,_fee numeric)` -> demande JSON. Sous verrou du profil, vérifier rôle chauffeur, solde courant >= débit, montant >=10 €, décimales exactes, frais égaux aux frais actuels, coordonnées bancaires présentes, aucune demande active. Insérer demande ET événement de notification durable dans la même transaction. NE PAS appeler wallet_entry ou create_payout ici. En cas de doublon réseau avec demande identique déjà pending, retourner cette même demande sans second événement ; montant différent : refuser.
4. RPC `approve_withdrawal(_request uuid,_actor uuid)` -> `{id,driver_id,status,payout_id,amount,fee,debit}`. Vérifier rôle admin de _actor, verrouiller d’abord profil puis demande (ordre identique partout), vérifier état et solde réel. Créer un payout early et les écritures comptables une seule fois avec la fonction existante, puis lier payout_id et passer processing dans LA MÊME transaction. Ne pas modifier les frais. Rejouer la même demande retourne le même payout_id sans débit ; paid retourne paid ; rejected/failed refuse. Un solde devenu insuffisant laisse la demande pending, aucun débit. Une validation processing n’appelle jamais une seconde fois wallet_entry.
5. RPC `reject_withdrawal(_request uuid,_actor uuid)` : vérification admin, verrouillage, état pending exclusivement, passage rejected sans écriture portefeuille. Aucun refus de processing : le fournisseur peut avoir reçu les fonds.
6. RPC `finish_withdrawal_request(_request uuid)` : lier l’état à la ligne payout. paid -> paid ; failed déjà recrédité par finish_payout -> failed ; pending reste processing. Idempotente. En cas de réponse Stripe incertaine, le code conserve processing et réessaie la même clé Stripe `payout-<payout_id>`. Après 24 h, ne pas relancer aveuglément un transfert dont la clé Stripe aurait expiré : réconcilier auprès de Stripe par payoutId et bloquer toute reprise tant que l’existence du transfert n’est pas établie. Traiter les refus définitifs avec finish_payout(false) une seule fois, puis synchroniser la demande.
7. Coordination : les virements hebdomadaires ignorent un chauffeur ayant une demande active (code préparé). Protéger aussi create_payout weekly sous le même verrou profil pour bloquer la course entre création de demande et virement automatique, en conservant toute la logique et les montants existants. L’approbation utilise un contexte transactionnel autorisé pour son payout lié.
8. RPC `record_withdrawal_notifications(_request uuid,_push_ok boolean,_email_ok boolean)` marque les succès avec OR, jamais de remise à false. RPC `pending_withdrawal_notifications(_limit integer)` retourne les demandes non notifiées, max25, avec lease/backoff pour éviter deux workers simultanés. Les événements survivent aux arrêts serveur. Aucune référence de demande envoyée depuis le navigateur ne peut devenir un événement arbitraire.
9. Planifier POST `/api/public/jobs/withdrawal-notifications` chaque minute avec l’authentification cron Lovable existante. Vérifier la tâche effectivement active. Prévoir expiration/alerte des événements non délivrés et ne pas faire tourner à l’infini une file sans destinataire inscrit. Programmer aussi la réconciliation des payouts processing avec Stripe, sans double transfert.
10. Configurer dans Secrets le compte Stripe réel adéquat, APP_URL, le connecteur Firebase Messaging existant et LOVABLE_API_KEY. Pour les e-mails : connecter Resend, domaine expéditeur vérifié, RESEND_API_KEY et PAYOUT_NOTIFICATION_FROM. Ne jamais mettre ces valeurs dans GitHub. Le code notifie les comptes portant le rôle admin, sur leurs e-mails Auth et leurs push_tokens. Tester les deux canaux sur un compte admin de test.
11. Push : le projet existant dispose de FCM Android/Capacitor ; le code prépare l’inscription des admins via `/api/notifications/push-token`. Sur un simple site iPhone/Safari, les push en arrière-plan ne sont PAS encore disponibles via ce module. Ajouter le Web Push adapté (PWA installée sur iOS >=16.4, service worker, permission explicite, abonnement stocké privé et routage) pour garantir l’alerte dans cet environnement. Ne pas présenter l’envoi d’e-mail comme une notification push. Respecter le refus de permission.
12. Vérifier les nouvelles mentions Conditions/Confidentialité, conserver demandes/écritures financières selon la rétention comptable existante et supprimer les jetons à la déconnexion. Adapter export et suppression de compte à la table (conservation légale anonymisée, pas de perte de comptabilité).

## Vérification obligatoire avant version 1

- Solde de 30 € : demande de 10 € -> solde 30 €, pending, événement durable ; validation -> solde20 €, payout9,50 €, frais0,50 € ; confirmation écran entier uniquement après insertion réussie.
- Tout le solde 30 € -> débit30 €, net29,50 € ; validation laisse0 €.
- 9,99 €, valeurs négatives, NaN, trop de décimales, frais falsifiés, solde insuffisant, client non chauffeur, non-admin approbateur -> refus sans débit.
- Deux demandes simultanées -> une seule active ; double validation et reprise après perte réseau -> une seule écriture et un seul transfert.
- Refus -> solde intact ; échec définitif Stripe -> recrédit unique ; timeout ambigu -> processing, aucune compensation prématurée ni nouveau payout.
- Course simultanée / dépense portefeuille / hebdomadaire -> verrous cohérents, pas de solde négatif ni double sortie.
- Push et e-mail réellement reçus, relance après arrêt serveur entre insertion et notification ; pas de notification pour une insertion échouée.
- Sélection de jour uniquement via L/M/M/J/V/S/D dans Revenus ; aucun nouveau champ de date.
- `npm run check:pricing` doit rester vert. Ne jamais régénérer son baseline.
